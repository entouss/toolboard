Core

Dynamic Tool

A tool you write on the board itself, in about ten lines.

Every other tool here arrives as a plugin somebody wrote, released and installed. Some jobs are too small for that and too particular to ever be worth it: the link you build by hand six times a day, the one number you keep opening a dashboard to read, the formula only your team uses. This is a window with four tabs — markup, a script, its data, and somewhere to read from — and whatever you put in them is a tool.

Add one to your board arrives working · nothing to install Open Toolboard

A new one starts as a working search-link builder, so there is something to read before there is something to write. Everything stays in your browser: the script runs on the page, and nothing is uploaded.

The four tabs

Body
HTML — the fields, buttons and places where the answer goes. Plain markup, not Markdown, because a script needs something to hold on to.
Script
JavaScript, run against that markup when the tool opens and whenever you change something. No build step and no boilerplate — the body of a function.
Data
The values the script reads, as JSON. This is the tab you come back to: the URL template, the field name, the threshold that turns the number red.
Source
A URL to read, and how often. What comes back is handed to the script, and the last answer is kept so the tool still draws when the network is down.

What your script is given

Four things, and nothing else to learn: 

function (el, data, api, source) { … }
  • el — this tool's own content area. Not the page, not the board, not the other copy of this tool two windows over.
  • data — the Data tab, parsed.
  • source — what the Source URL returned, or null when there isn't one. Parsed as JSON where it is JSON, handed over as text where it isn't.
  • api.save(value) — store value as this tool's data. It survives a reload and appears in the Data tab, so the state is visible rather than hidden.
  • api.onCleanup(fn) — run fn when the tool is closed, re-run, or the board switches away. Anything you start, stop here.
  • api.reload() — read the Source URL again now, whatever the schedule says.

Why source is separate from data. A tool that reads a feed almost always has settings too — which field, what to call it, when to go red. Folding the two together would force one of them to live in the code, which is the thing the Data tab exists to avoid.

Three worth copying

A live number Source + schedule

Put a URL in Source, set a refresh, and name the field in Data. The tool draws the cached answer the instant the board opens, then replaces it when the read lands. 

el.querySelector('.n').textContent =
    source ? source[data.field] : '—';

Data: { "field": "count" } · Source: your endpoint, refresh every 60 seconds.

A form that writes the thing you were going to type Body + Data

Commit messages, standup lines, a kubectl incantation, an address block. Fill the fields, press the button, paste the result. 

const get = (c) => el.querySelector(c).value;

el.querySelector('.go').onclick = () => {
    const text = data.template.replace(
        /\{(\w+)\}/g, (m, k) => get('.' + k));
    el.querySelector('.out').textContent = text;
    copyTextToClipboard(text, 'Copied');
};
A roll-up of the other tools on the board The one a plugin would be needed for

The script runs on the page, so it can read what the rest of the board holds — here, every checklist on it at once. 

let done = 0, open = 0;
Object.values(toolCustomizations).forEach(c =>
    (c.checklistItems || []).forEach(i =>
        i.status === 'done' ? done++ : open++));

el.textContent = done + ' done, ' + open + ' to go';

What it is good for

The question that decides it: does this need to exist in a repository, or just on your board?

  • Link builders and launchers. Ticket IDs, internal search, an environment dashboard. The templates live in Data, so adding a destination is editing JSON.
  • Live readouts. A status endpoint, an open-issue count, a rate, a queue depth. One number, fresh when you look at it.
  • Calculators with your own formula. The ones no generic tool ships: pricing, a trade conversion, a rule of thumb. Constants in Data, formula in Script.
  • Form to formatted text. Kills the small tasks you were going to do by hand again.
  • Counters, tallies and logs. api.save means persistence is already solved.
  • Clocks, countdowns and timers. api.onCleanup keeps them honest when the board changes.
  • Paste-in, paste-out transformers. A regex you keep re-deriving, date arithmetic, decoding a format only your company uses.
  • Glue between tools. Summarising or cross-checking what another tool on the board holds — otherwise a plugin.
  • A prototype that earns its way in. Live with it for a week; if it survives, lift the script into a plugin. Most ideas don't survive the week, and this is the cheap way to find out which.

Where it stops

  • Anything wanting tests and review belongs in a plugin file, in version control.
  • Libraries. One function body, no build step. You can reach out to a CDN at runtime, but the shape rewards small.
  • Secrets. All four tabs travel in an export. An API key in Data is a key you have shared.
  • Hosts that forbid cross-origin reads. A read is tried directly and then through the board's proxy, which answers only the published site — so a feed that works on toolboard.me may not work on a copy you host yourself, and the Source tab says which route the data came by.
  • Elaborate interfaces. No stylesheet of your own — inline styles or the board's theme variables, in a window the size of a window.
  • Errors from your own handlers. A throw while the script is running is caught and shown in the tool. One thrown later, from a click handler it installed, goes to the browser console like any other page's would.

Sharing one, and running someone else's

A dynamic tool exports like any other tool, and a board template can carry one. What that means is that a board can now arrive with code in it — so it arrives switched off.

  • The markup and the data are drawn; the script does not run. The tool says so, and offers Review — which puts the code in front of you — and Run it.
  • What is recorded when you press Run is the exact script text you approved, never a yes-or-no. So a linked source that re-fetches unchanged keeps running, and the same source pushing different code next week stops and asks again.
  • That approval never leaves your browser. An approval carried in a file would be the file approving its own script.

This is not a sandbox. A script that runs here can do anything the page can. That is fine for code you wrote, and it is exactly why code that arrives waits to be read. Read it before you press Run — the same care you would give a shell command somebody sent you.
